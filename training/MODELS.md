# 模型登记表（行走 / 射门 / 起身）

本文件记录在 AMD GPU（Genesis + ROCm）上训练的所有行走、射门和起身模型，包括每个版本的来历、改动、评估结果和结论，方便日后挑选模型、了解开发历史。**每训练或评估一个新版本，都要在这里登记**（见 §6）。

- 训练硬件：AMD Radeon AI PRO R9700 单卡，每次训练 4096 个并行环境
- 指标由 [`collect_metrics.py`](collect_metrics.py) 从 `evals/` 统一重新计算，不要手抄
- 最后更新：2026-11-17（起身 / 站立模型 stand-B）

**状态图例**：✅ 推荐　🟡 可用（有特定用途）　🔬 实验（有价值但还不能直接用）　❌ 淘汰　📌 基线（对照用）

### 2.4 起身 / 站立（stand：跌倒后起身，以及射门后 1 秒的平衡交接）

游戏里 `stand` 模型有两个用途：机器人倒地 0.28 s 后先保持 0.22 s，再由 `stand` 把它扶起来，直立 0.6 s 后交还给行走；以及学习型射门结束后的 1 秒平衡。评估见 §3 的 `evaluate_stand.sh`（数字由 `summarize_stand_eval.py` 生成）。

| 版本 | 状态 | 一句话 | 起身测试：成功 / 强制归位 / 再次跌倒 | 起身用时 中位 / 最慢 | 配 walk-A：成功 / 强制归位 | 射门交接倾角（v4ft / v5+walk-A） | 原作者组合比赛：进球 / 跌倒 / 归位 | 全 AMD 组合：进球 / 射门→进球 / 跌倒 / 归位 |
|---|---|---|---:|---:|---:|---:|---:|---:|
| 官方 BEST_alpha_stand | 📌 | Pollen 在 mjlab 上训练 | 59/59 / 0 / 3 | 0.62 s / 4.60 s | 55/58 / **3** | 12.5° / 12.1° | 61 / 10 / 0 | 93 / 96% / 2 / 0 |
| stand-A | ❌ | 上游配方原样移植；4500 轮仍学不会从躺倒起身 | – | – | – | – | – | – |
| stand-B-2000 | 🔬 | B 的早期 checkpoint | 59/59 / 0 / 0 | 0.66 s / 1.68 s | 58/58 / 0 | 12.6° / 12.4° | 62 / 12 / 0 | 93 / 96% / 2 / 0 |
| stand-B-4500 | 🔬 | 起身更快，交还行走后更稳 | 59/59 / 0 / 1 | 0.58 s / 1.26 s | 58/58 / 0 | 13.1° / 12.8° | 47 / 9 / 0 | 92 / 95% / 2 / 0 |
| **stand-B-9999** | ✅ | 已上线 `?stand=genesis`；**没有一次失败，最慢 0.84 s** | **59/59 / 0 / 0** | 0.62 s / **0.84 s** | **58/58 / 0** | 12.7° / 12.4° | 60 / 10 / 0 | 90 / 94% / 3 / 0 |

- **起身测试**（S6，60 个用例，游戏 MuJoCo + 游戏真实的倒地 → 起身 → 交还行走流程）：趴、仰、左右侧躺、坐姿各 4 个朝向，24 个随机姿态掉落，16 个 1.2 m/s 侧推。"再次跌倒"= 交还行走后又倒下；"强制归位"= 7 s 内没站起来，游戏把机器人瞬移复位。
- **配 walk-A 时官方模型会失败 3 次**：倒地后前 0.28 s 仍由行走模型控制腿，walk-A 留下的姿态官方起身模型不一定能处理。stand-B 在训练里见过随机姿态掉落，60 个用例全部成功。
- 比赛的总进球差异来自 2v2（同一局里的微小差异会导致完全不同的走向）；**8 个单人场景的进球与官方完全相同**（原作者组合 29–31 球，全 AMD 组合 44 球），跌倒和归位次数也没有变差。

## 3. 评估协议

每个新版本都要跑完这两项，指标才能和表里的数字直接比较：

| 对象 | 命令 | 测什么 |
|---|---|---|
| 射门 | `./evaluate_candidate.sh <exp> <ckpt> <gpu>` | 导出 ONNX + manifest；S4 的 18 个用例在两个引擎里各跑一遍；游戏评估器 11 个场景（配官方行走） |
| 行走 | `./evaluate_walk.sh <exp> <ckpt>` | S1 的 14 个场景 + 从静止出发的 19 个指令扫描（游戏 MuJoCo）；配射门模型打比赛（默认 v4ft-v3，可用 `FOOTBALL_ONNX=` 换） |
| 起身 | `./evaluate_stand.sh <exp> <ckpt>` | S6 起身测试 60 个用例（游戏默认行走和 walk-A 各一遍）；S4 射门交接（v4ft、v5+walk-A）；两套组合打比赛（原作者组合只换起身模型；全 AMD 组合 walk-A + v5） |
| 汇总 | `collect_metrics.py` / `summarize_stand_eval.py` | 重新算出本文所有表格的数字 |

**指标定义**（与 `collect_metrics.py` 一致）：
- **射门→进球**：射门后 5 秒内有进球的比例
- **踢球跌倒**：跌倒发生在射门窗口或交接阶段之后 1.6 s 内
- **强制归位**：起身失败超过 7 s，游戏把机器人强制复位。展台上最需要避免
- **S4 交接后倾角**：交接给 `stand` 之后 0.6 s 内的最大倾角，取 18 个用例的中位数。原作者是 5.6°，越小越好
- **S4 球速**：18 个用例球峰值速度的中位数（m/s）

**2v2 的进球数不能直接用来比较行走模型**：2v2 里四个机器人用同一个行走模型，走得快的模型同时也是更好的防守者，进球数会被压低。比较行走模型时，主要看**单人场景**（射门→进球、单位时间射门次数、跌倒）；2v2 主要用来看跌倒和卡死。`collect_metrics.py` 会单独输出这两组数字。

**注意**：游戏评估是**确定性的单次运行**，但结果对细微差异非常敏感。例如 walk-D1 的行走指标和 walk-A 几乎一样，比赛却是 17 球对 71 球。随机波动的幅度还没有量化，**进球差几个球时不要据此下结论**；对外引用数字前要做多随机种子统计。

## 4. 版本详情

每条记录的字段：基于 / 改动 / 训练 / 文件 / 游戏开关 / 结论。完整配方在 `logs/<run>/recipe.json`。

### 射门

**原作者 football**（📌 基线）
- 来源：soccer 游戏作者用 mjlab 在 NVIDIA 上训练（1024 环境 × 2000 轮），游戏默认使用，`public/assets/policies/football.onnx`
- 特点：交接平稳（5.6°）；配官方行走 61 球、跌倒 10 次（全部是冲撞或碰撞，不是踢球引起）

**football-v1**（❌）
- 基于：从头训练。配方：踢球奖励 3/步，站姿类奖励合计约 8.5/步
- 训练：2000 轮，1 h 21 min
- 结论：触球率在第 50 轮达到 52% 后掉回约 9%，学成了"站着不动"。教训：**任务奖励必须明显大于站姿奖励**

**football-v2a**（❌，后续版本的配方基础）
- 改动：踢球奖励 3 → 10；新增一次性触球奖励 2；靠近球的引导奖励 1 → 3；站姿类奖励降到合计约 3.5/步。**现在 `football_cfg.py` 的默认值就是这套配方**
- 训练：从头 2000 轮，1 h 43 min。文件 `football-v2a-1999`（sha `e39a7553`，只在本地）
- 结论：进球 74，但踢球跌倒 4/81，交接后倾角 30.9°

**football-v2b**（❌）
- 改动：v2a 基础上踢球奖励改为 20、触球奖励改为 5（`--set REWARD_WEIGHTS.ball_speed_along_aim=20 --set TOUCH_BONUS=5`）
- 训练：从头 2000 轮，1 h 26 min。文件 `football-v2b-1999`（sha `d1dbb978`，只在本地）
- 结论：球速 2.7 m/s，太猛；左脚在 MuJoCo 里偏 −14°（只在 MuJoCo 出现，与接触参数无关，原因是动作过于激进）。单人场景每局约 1 球

**football-v3**（❌）
- 改动：v2a 基础上超速惩罚 −10、横向偏离惩罚 −6、新增转身惩罚 −1
- 训练：从头 2000 轮，1 h 26 min。文件 `football-v3-1999`（sha `a6bf9551`，只在本地）
- 结论：自己控制的窗口内很稳（< 15°），但交接给官方 stand 后晃到 43°，S4 里 3/18 跌倒。教训：**问题出在交接兼容性**

**football-v4**（❌）
- 改动：v3 基础上 `HANDOFF_IN_LOOP=True`：1.2 s 后训练环境改用官方 stand（1 s）和 walk（0.3 s）
- 训练：从头 2000 轮，1 h 29 min。文件 `football-v4-1999`（sha `c5cba6c0`，只在本地）
- 结论：44 球，跌倒 25。回合 2.5 s 中只有约一半样本属于踢球窗口，从头训练 2000 轮不够

**football-v4ft-v2a**（❌）
- 改动：v4 的配方，从 v2a-1999 继续训练 1000 轮
- 训练：47 min。文件 `football-v4ft-v2a-2998`（sha `d6595ad9`，只在本地）
- 结论：76 球、交接后倾角 6.9°，但出现 1 次强制归位（起身失败），展台不能接受

**football-v4ft-v3**（🟡，已上线 `?football=genesis`）
- 改动：v4 的配方，从 v3-1999 继续训练 1000 轮
- 训练：43 min。文件 `exports/football-v4ft-v3-2998.onnx`（sha `dbde067d`，已提交）
- 结论：第一个全面不输原作者的版本（68 球，踢球跌倒 0，强制归位 0，交接后倾角 12.5°）。射门只在"标准站姿、静止"状态下训练过；配 D2 快步态时射门→进球只有 37%

**football-v5**（✅，已上线 `?football=genesis-v5`）
- 改动：v4ft-v3 基础上 `PREROLL=True`：每回合先由行走策略走 0.6–2 s，D2 和 walk-A 各一半，最后模仿 AI 的停下对准动作；然后按机器人当时的姿态放球，再起脚。75% 的回合有这段前置行走；前置阶段不计奖励、跌倒不扣分
- 训练：从 v4ft-v3-2998 继续训练 1500 轮，1 h 09 min。文件 `exports/football-v5-4497.onnx`（sha `538c0e7d`，已提交）
- 结论：**配 walk-A 进 93 球**（射门→进球 96%）；配 D2 时射门→进球从 37% 提升到 74%。**配官方行走很差**（24 次跌倒、3 次强制归位）

**football-v5-D2**（🟡）

**walk-E3**（🟡，已上线 `?walk=genesis-fast`；目前最好的快步态）

- 结论：前进 0.203 m/s（walk-A 的 1.9 倍），转向 1.02 / 1.45，停稳用时 0.04 s，走走停停滑行 4.2 cm，**行走指标全面达到或超过 walk-A**。但配 v5 只进 52 球（射门→进球 75%），走位时碰到球的次数（约 54 次）仍远多于 walk-A（9 次）

  - 只拉开站位距离：50–55 球，没有改善
  - 接近目标时减速：进球升到 68–77，但跌倒增加到 16–18 次，不可用
  - 碰球次数在所有组合下都在 54–60 之间，说明碰球不是由接近速度或距离引起的
  - 等身体不再转动后才射门，并改用按比例转向：50–53 球，跌倒增加
- 用 E3 做前置行走重新训练射门（v6、v6-E3）：单人场景准确率略升到 95–97%，2v2 没有稳定改善
- 结论：**作为快步态，行走层面已可用**；要让比赛节奏也受益，需要为快速机器人设计的比赛 AI（方案 ③ 中自研）

**walk-D3**（🔬）：从 walk-A 继续 3000 轮。步频窗口放宽到 0.4 s，抬脚高度和摆动高度目标 2 → 3 cm，前进跟踪权重 2 → 3。速度 0.166 m/s，转向好。文件 sha `d23e319d`，只在本地。

## 6. 如何登记新版本

1. **命名**：`<任务>-<变体>`，例如 `football-v6`、`walk-E1`；导出文件为 `<名字>-<checkpoint>.onnx`。fine-tune 版本用 `ft` 标出基于谁，例如 `v4ft-v3`。
2. **训练**：用 `train_football.py`、`train_walk.py` 或 `train_standup.py`，配方改动一律用 `--set`。配方会自动存到 `logs/<run>/recipe.json`。
3. **评估**：按 §3 跑完；射门模型还要和推荐的行走组合测一次（`FOOTBALL_ONNX=... ./evaluate_walk.sh --onnx walk-A-5998 exports/walk-A-5998.onnx`）。
4. **更新本文件**：
   - 运行 `collect_metrics.py`，把新数字填进 §2 的表（只用脚本算出的数字）
   - 在 §4 加一条记录，用下面的模板
   - 如果推荐有变化，更新 §1；有新教训的话补进 §5
5. **决定是否提交**：只有推荐（✅）或上线的版本才把 ONNX 加进 `.gitignore` 白名单并提交；其他版本只登记 sha256。

```markdown
**<版本名>**（<状态>，<游戏开关或"未加入游戏">）
- 改动：<基于哪个 checkpoint；相对基础配方的 --set 列表>
- 训练：<环境数 × 轮数，用时>。文件 `<exports/xxx.onnx>`（sha `<前 8 位>`，<已提交 / 只在本地>）
- 结论：<关键指标；与上一版相比；适合什么搭配；已知问题>
```

